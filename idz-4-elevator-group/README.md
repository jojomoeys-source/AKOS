# Группа лифтов

Индивидуальное домашнее задание № 4, вариант 29.

Программа моделирует работу группы лифтов с общим диспетчером. Диспетчер,
каждый лифт и каждый пассажир работают в отдельных дочерних процессах. TCP-сервер
передаёт события модели клиентам-наблюдателям. Состояние модели хранится в POSIX
shared memory, процессы синхронизируются POSIX-семафорами.

## Сборка и запуск

```bash
cmake -S . -B build
cmake --build build
./build/elevator --config data/many-passengers.txt --host 0.0.0.0 --port 5050
```

Без `--config` программа запрашивает параметры в терминале. Ключ `--log FILE`
задаёт файл журнала, `--help` выводит справку. По умолчанию TCP-сервер слушает
`127.0.0.1:5050`; чтобы принимать подключения с других компьютеров, укажите
`--host 0.0.0.0`.

Справка выводится командой `./build/elevator --help`. Если путь к журналу не
указан, используется файл `elevator.log`. Программу можно остановить сочетанием
`Ctrl+C`; перед завершением она выводит состояния недоставленных пассажиров.

Перед первым модельным тактом программа ждёт три секунды, чтобы клиент успел
подключиться. Задержку можно изменить ключом `--start-delay MS` или отключить,
указав `--start-delay 0`.

Клиент-наблюдатель на этом же компьютере:

```bash
./build/elevator_monitor --host 127.0.0.1 --port 5050
```

На другом компьютере вместо `127.0.0.1` укажите IPv4-адрес машины с сервером.
Можно запустить несколько наблюдателей. Новый клиент получает события с момента
подключения; отключение или повторное подключение наблюдателя не останавливает
модель. При завершении моделирования сервер закрывает клиентские соединения.

## Независимые процессы

Сначала соберите проект и перейдите в каталог задания:

```bash
cmake -S . -B build
cmake --build build
cd build
```

Подготовьте общую память и семафоры по конфигурации:

```bash
./elevator_setup ../data/simple.txt
```

Затем запустите один диспетчер, по одному процессу на каждый лифт и пассажира.
Для конфигурации `simple.txt` нужны один лифт и один пассажир:

```bash
./elevator_dispatcher &
./elevator_lift 0 &
./elevator_person 0 &
```

Когда все участники запущены, управляющий процесс начинает моделирование и
ожидает окончания:

```bash
./elevator_run
wait
./elevator_cleanup
```

Индексы лифтов и пассажиров начинаются с нуля. При другом количестве участников
запустите соответствующее число процессов с индексами от `0` до `N - 1`.
Участников нужно запустить до `elevator_run`. Они используют общую память и
записывают события в `elevator.log`. В независимом режиме TCP-сервер не запускается.
Если запуск был прерван до очистки ресурсов, выполните `./elevator_cleanup`.
Опция `--unnamed-semaphores` у `elevator` включает вариант с неименованными
семафорами в общей памяти. Этот режим требует Linux с поддержкой `sem_init` и
`pshared`.

## Входные данные

Программа последовательно читает:

1. количество этажей, лифтов и пассажиров;
2. вместимость и начальный этаж каждого лифта;
3. минимальный и максимальный интервал появления пассажиров;
4. скорость движения в этажах за такт;
5. время открытия дверей, посадки и высадки;
6. стратегию диспетчера;
7. период работы в тактах;
8. этажи отправления и назначения пассажиров.

Стратегия `1` выбирает ближайший свободный лифт. Стратегия `2` сначала ищет
попутный лифт, затем ближайший свободный. Нулевой период работы означает, что
программа работает до доставки пассажиров.

Формат конфигурационного файла:

```text
этажи
лифты
пассажиры
вместимость_лифта_1 начальный_этаж_лифта_1
...
минимальный_интервал максимальный_интервал
скорость
время_открытия_дверей
время_посадки
время_высадки
стратегия
период_работы
этаж_отправления_1 этаж_назначения_1
...
```

Время появления пассажиров накапливается из интервалов заданного диапазона. Если
границы совпадают, время появления воспроизводимо.

## Процессы модели

Основной процесс создаёт дочерние процессы диспетчера, лифтов и пассажиров.
Пассажир ждёт времени появления, регистрирует вызов и ожидает доставки. Диспетчер
берёт вызовы из общей очереди и назначает лифт. Лифт обрабатывает движение,
остановки, двери, посадку и высадку. Главный процесс продвигает модельное время
после того, как все лифты завершили текущий такт.

## Синхронизация и обмен событиями

Состояния пассажиров, лифтов и очередь вызовов находятся в POSIX shared memory.
Семафор `stateLock` защищает общие данные, а `callsAvailable` сообщает диспетчеру
о новых вызовах. Барьер `completedLiftCount` не позволяет главному процессу
начать следующий такт до завершения текущего всеми лифтами.

Дочерние процессы записывают события в pipe главного процесса. Главный процесс
публикует их по TCP-серверу, работающему в отдельном дочернем процессе. Сервер
принимает источник событий и подключения наблюдателей, затем пересылает сообщения
всем активным клиентам. Клиент только читает и показывает полученный поток.

## Работа модели

Открытие дверей, посадка и высадка занимают заданное число тактов. Пока выполняется
одна из этих операций, лифт не движется. Вместимость кабины не превышается;
пассажир входит на этаже отправления и выходит на этаже назначения.

В терминале и у подключённых клиентов отображаются появление пассажира,
регистрация и назначение вызова, движение и прибытие лифта, работа дверей,
посадка, высадка и доставка.

Моделирование завершается после доставки всех пассажиров, окончания периода
работы или получения `SIGINT` (`Ctrl+C`). В последних двух случаях выводятся
состояния недоставленных пассажиров. После остановки освобождаются общая память и
семафоры, TCP-сервер закрывает соединения наблюдателей.

## Тестирование

Тесты запускаются командой:

```bash
ctest --test-dir build --output-on-failure
```

CTest содержит сценарии простого маршрута, ограничения вместимости,
противоположных направлений, пассажиров с одного этажа, разных начальных этажей,
одновременных вызовов, повторного назначения при занятых лифтах и завершения по
рабочему периоду. Все девять сценариев прошли на машине разработки.

Отдельно проверено сетевое подключение двух наблюдателей: один отключился и
подключился повторно во время поездки, второй оставался подключённым до
завершения модели. Оставшиеся клиенты получили сводку и сообщение о закрытии
соединений. Также проверено завершение по Ctrl+C с двумя подключёнными
клиентами: оба получили сообщение об остановке и завершились при закрытии
соединений сервером.

## Структура программы

```text
main                     запуск модели и освобождение ресурсов
input                    чтение и проверка входных параметров
process_simulation       дочерние процессы и модельное время
shared_state             POSIX shared memory
shared_queue             общая очередь вызовов
ipc_sync                 POSIX-семафоры
person_process           процесс пассажира
dispatcher_process       процесс диспетчера
lift_process             процесс лифта
independent_*_main       отдельно запускаемые программы
independent_worker       работа независимых процессов
dispatcher               выбор подходящего лифта
actions                  завершение действий с таймерами
service                  двери, посадка и высадка
route                    выбор следующей остановки
lift                     состояние и движение лифта
person                   состояние пассажира
tcp_events               TCP-сервер и передача событий
monitor_main             клиент-наблюдатель
logger                   вывод событий и журнала
statistics               итоговая статистика
interruption             обработка SIGINT
```
